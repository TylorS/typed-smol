## Key Findings

- The existing durable virtual-modules spec conflicts with current code. The spec says virtual files are always `typed-virtual://` and not disk paths, while `createVirtualFileName` already returns `node_modules/.typed/virtual` paths when `projectRoot` is provided.
- The current cache is process-local. `VirtualRecordStore` and `TypeInfoApi` caches do not provide a manifest-backed, cross-process artifact store.
- Vite, vmc, TS plugin, and VS Code do not share one materialization path today. Vite uses encoded virtual IDs and resolver calls, vmc creates compiler-host source files in memory, the TS plugin uses the language-service adapter, and VS Code has separate disk-preview logic.
- The current artifact identity hash is based on importer plus id. It does not include source hashes, plugin implementation/config fingerprints, TypeScript version, or parsed tsconfig.
- Disk materialization uses regex-based import rewriting. That is too narrow for a production-generated artifact layer unless the supported import syntax is explicitly constrained.
- `vmc --watch` needs targeted validation because the compiler-host adapter appears to be disposed immediately after builder-program creation.
- Vite's virtual-module convention supports the idea of a logical virtual identity distinct from the generated backing file. Keeping `typed-virtual://` as the logical identity is compatible with this direction.
- Vite's Environment API is not a stable enough foundation for the first compiler-substrate tranche. Environment-plugin work should remain later-phase research/spec input.
- SvelteKit provides useful precedent for generated hidden framework artifacts and generated type surfaces, but Typed should keep cache persistence by default because this workflow's goal is shared generated-artifact reuse, not disposable build output.

## Open Risks and Unknowns

- Exact manifest schema is not specified yet.
- Exact logical-identity to physical-path mapping is not specified yet.
- The implementation strategy for robust import rewriting is not specified yet.
- Plugin fingerprint implementation details may vary between package-loaded plugins and preloaded plugin objects.
- Cross-process safety needs tests that can run reliably in the repo's toolchain.

## Implications for Requirements and Specification

- Requirements must include both per-artifact manifests and a project-level index.
- Requirements must treat source/config/plugin/compiler fingerprints as the correctness boundary for cache reuse.
- Specification must create or update a durable virtual module artifact-store contract; this cannot live only in workflow notes.
- Specification must preserve `typed-virtual://` as logical identity and treat `node_modules/.typed/virtual` as physical backing.
- Specification must define diagnostics storage in the manifest and consistent surfacing across vmc plus at least one dev/editor surface.
- Specification must address concurrency with atomic writes and last-valid-writer-wins.

## Memory Promotion Candidates

- procedural: Use manifest-backed generated artifacts as the compiler substrate before adding higher-level app virtual module surfaces. Confidence: high after specification approval.
- heuristic: Keep `typed-virtual://` as logical identity and map it to persistent `node_modules/.typed/virtual` artifacts. Confidence: medium until spec/ADR approval.
- mistakes: Do not rely on process-local virtual record caches or regex-only import rewriting for productionized generated artifacts. Confidence: high.
